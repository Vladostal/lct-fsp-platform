# ФСП.Подбор

Платформа подбора ИТ-специалистов с обратной механикой (ЛЦТ-2026, спецтрек ФСП). Категорию кандидата —
специализацию и грейд — определяет тест, а не резюме; там, где тест ещё готовится, грейд заявленный, и это
подписано на каждой карточке. Работодатель описывает потребность, получает подборку
с объяснением и сам отправляет приглашение с вилкой в рублях. Контакты кандидата открываются только после того,
как он принял приглашение.

## Быстрый запуск

Нужны Docker и Docker Compose.

```bash
cp .env.example .env
docker compose up --build -d
```

Первый запуск занимает около двух минут: сервис `migrate` создаёт схему, собирает банк заданий, демо-реестр ФСП
и демо-данные, после чего поднимаются `api` и `web`.

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:8080 |
| Демо-аккаунты и вход «как…» | http://localhost:8080/demo |
| Почтовый ящик стенда (письма подтверждения) | http://localhost:8080/mail/ |
| Swagger платформы | http://localhost:8080/api/docs |
| Swagger демо-реестра ФСП | http://localhost:8080/api/fsp-mock/docs |

Остановить: `docker compose down`. Удалить данные: `docker compose down -v`.

Для публичного стенда `.env` создаёт `make init-env`: случайные секреты, закрытый почтовый ящик. Дальше вручную
задаются `APP_ENV=production`, `PUBLIC_BASE_URL=https://…`, `COOKIE_SECURE=true` и адрес внешнего прокси
`NGINX_REAL_IP_FROM`. С учебными секретами в режиме `production` приложение не стартует.

## Сквозной сценарий для показа

1. Регистрация кандидата, письмо подтверждения в ящике `/mail/`.
2. Профиль (вручную или из PDF-резюме) → опрос → выбор грейда → тест → категория.
3. Работодатель описывает потребность текстом, правит разобранные поля, получает подборку.
4. Уточнение запроса создаёт новую версию подборки; прежние версии остаются, видны различия.
5. Приглашение кандидату с вилкой; кандидат принимает и выбирает, какие контакты открыть.

Готовые состояния каждого шага есть в именованных демо-аккаунтах на странице `/demo`.

## Как устроено

Модульный монолит на FastAPI, PostgreSQL, SPA на React. Наружу опубликован только nginx сервиса `web`: он раздаёт
статику и проксирует `/api` и `/mail/`.

```
web (nginx + SPA) ──/api──▶ api (FastAPI, один процесс) ──▶ db (PostgreSQL 18)
        │                         │
        └──/mail/──▶ mailpit      └── демо-ФСП: OIDC-провайдер и реестр, смонтированы в /api/fsp-mock
```

Модули бэкенда (`backend/app/modules`), снизу вверх по слоям; импорт разрешён только вниз и только через
`service.py` и `dto.py` — это проверяет `import-linter`:

| Слой | Модули | Что делают |
|---|---|---|
| 1 | `identity`, `catalog`, `reports` | аккаунты, сессии, согласия; справочники; сводки отчётов валидации |
| 2 | `company`, `textparse` | профиль компании; разбор текста потребности и резюме по правилам |
| 3 | `assessment` | опрос, банк заданий, сессия теста, правила грейда |
| 4 | `profile`, `fsp` | профиль кандидата, приватность, раскрытие контактов; привязка ФСП ID и достижения |
| 5 | `matching` | потребности, подборка, объяснение, версии подборки, банк кандидатов |
| 6 | `contact` | приглашения, статусы, раскрытие контактов |
| 7 | `demo` | демо-аккаунты и перезапуск сценария |

Чистые ядра без базы данных (`assessment/engine`, `matching/scoring.py`, `matching/ranking.py`, `fsp/signal.py`,
`contact/rules.py`) вызываются и сервисом, и симуляциями валидации из `backend/app/eval`.

### Тестирование

- Задание — не текст, а **генератор**: по числу-сиду он строит условие и вычисляет верный ответ кодом. В банке
  31 семейство заданий, у каждого 2–3 уровня сложности и по 60 вариантов на уровень. Нейросеть в выдаче заданий
  не участвует.
- Каждому кандидату собирается своя форма из 14 заданий по плану тем грейда; если результат на границе,
  добавляются блоки по 6 заданий (до 26). Утёкший ответ не подходит к другому варианту того же задания.
- Уровень оценивается по всем ответам за 180 дней. Исходы: подтверждён с запасом, подтверждён, на границе,
  не подтверждён. Грейд принудительно не понижается: не подтвердил — можно пройти тест на грейд ниже,
  подтвердил с запасом — на грейд выше. Смена подтверждённого грейда — не чаще раза в 90 дней.
- Тест есть для Backend. В остальных девяти специализациях кандидат после опроса **заявляет грейд**: категория
  получает основание «заявлен» (`basis = declared`), уровня по тесту у неё нет, работодатель видит пометку
  «заявлен, тест готовится». Первую смену заявленного грейда можно сделать сразу, следующие — раз в 90 дней.
  Для Backend категория по-прежнему появляется только после теста.
- «Из вакансии в тест»: страница «Как это работает» и `POST /api/v1/assessment/blueprints/preview` показывают,
  как описание вакансии меняет план теста.
- Ответы, данные быстрее, чем читается условие, помечаются. На результат это не влияет; пометка видна
  в служебной сводке банка как признак утечки вариантов.

### Подбор

1. Условия: общий формат работы. Кто не проходит — в подборку не входит.
2. Разделы категорий: основная, грейд ниже с запасом, грейд выше. Разделы не смешиваются.
3. Порядок внутри раздела: число закрытых обязательных навыков → подтверждённое покрытие (тест и ФСП) →
   сила профиля → покрытие заявленным.
4. У каждой строки — доводы и риск: что подтверждено тестом, что заявлено кандидатом, по чему нет данных.

Потребность и поиск по банку доступны по всем десяти специализациям. Там, где теста нет, в подборке кандидаты
с заявленным грейдом: первым доводом у каждого стоит «грейд заявлен кандидатом: тест по специализации готовится»,
в раздел «грейд ниже с запасом» они не попадают, «подтверждён недавно» про них не пишется.

Сила профиля (версия оценщика `match-3`) — до 100 баллов:

| Часть | Баллы | Источник |
|---|---|---|
| Результат теста (нижняя граница оценки, с учётом давности) | до 10 | подтверждено |
| Достижения ФСП | до 30 | подтверждено |
| Стаж; полный вклад при 2 / 5 / 8 годах для junior / middle / senior | до 35 | заявлено кандидатом |
| Навыки своей специализации из профиля; полный вклад при шести | до 25 | заявлено кандидатом |

60 баллов из 100 — заявленное. ТЗ просит ранжировать внутри категории по подтверждённому профилю, поэтому
заявленное ограничено: оно насыщается (стаж и навыки сверх порога ничего не добавляют), одним заявленным без ФСП
не набрать подпись «высокая» (нужно 65, потолок 60), а в порядке сила стоит третьей — после закрытых обязательных
навыков и подтверждённого покрытия, куда заявленное не входит. В карточке вклады разделены на «подтверждено»
и «заявлено кандидатом». Скрытые настройкой приватности стаж или стек вклада не дают. Если заявленный стаж ниже
обычного для грейда (middle — от 2 лет, senior — от 5) или не указан при заявленном грейде, в объяснении
появляется пометка; на порядок она не влияет.

Достижения ФСП только добавляют к силе профиля: у кандидата без истории ФСП вклад равен нулю, штрафа нет.
Банк кандидатов (поиск по всей базе с фильтрами) упорядочен по силе профиля внутри категории.

### Контакт

Вилка обязательна в потребности и в приглашении. У работодателя ограниченное число одновременных приглашений,
у кандидата 7 дней на ответ. Скрытый минимум кандидата сверяется с нижней границей вилки при отправке:
работодатель видит только «условия не совпали». Имя и контакты в карточке, подборке и PDF появляются только
после принятия приглашения, и только те каналы, которые выбрал кандидат.

### Интеграция с ФСП

Привязка ФСП ID — поток OIDC Authorization Code с PKCE, `state` и `nonce`. Платформа получает только
идентификатор участника и с его согласия запрашивает выгрузку из реестра. Внутрь попадает собственная модель
достижений; сырые ответы реестра наружу не отдаются. Демо-провайдер и демо-реестр — отдельное ASGI-приложение
`backend/app/fsp_mock`; его контракт выгружен в `docs/fsp-registry-openapi.json`. Обрабатываются отказ на странице
входа, занятый ФСП ID, несовершеннолетний участник, участник без результатов, недоступность и некорректный ответ
реестра. Адаптер для настоящего Keycloak (`FSP_MODE=keycloak`) в этой сборке не реализован.

## Валидация

Данных о реальных наймах нет, поэтому механики проверяются симуляцией на синтетических популяциях. Отчёты лежат
в `docs/validation/*/report.json`, пересобираются командой `make eval`, сводка показана на странице
«Как это работает».

| Механика | Показатель | Значение |
|---|---|---|
| Подбор | P@10, наш порядок | 0,543 |
| Подбор | P@10, сортировка по заявленным навыкам | 0,499 |
| Подбор | P@10, только сила профиля | 0,380 |
| Подбор | P@10, случайный порядок в категории | 0,335 |
| Подбор | P@10 без теста (все грейды заявленные): наш порядок / заявленные навыки / случайный | 0,444 / 0,418 / 0,260 |
| Тестирование | точность исхода против истинного уровня | 0,921 |
| Тестирование | согласие решения при повторном тесте | 0,829 |
| Тестирование | ложное подтверждение при пяти утёкших сессиях | 0,243 |
| Контакт | доля принятых приглашений | 0,474 |

В отчёте подбора (`match-3`) не выполнены два критерия из десяти, и они так и напечатаны. Первый: на потребностях,
где все обязательные навыки проверяет тест, наш порядок не лучше сортировки по одной силе (разность P@10 −0,007,
интервал [−0,044; +0,029]). Второй: накрутка заявленным меняет первый ключ порядка — дописанный навык закрывает
пробел в обязательных у 71,5 % накрутивших; подтверждённое покрытие она не меняет ни у кого. Перенос 60 баллов
силы на заявленное P@10 не изменил: разность с прежней силой `match-2` (тест 70, ФСП 30) −0,001 [−0,003; +0,001].
Цена решения видна в другом: кандидаты с ФСП вытесняют из первой десятки по силе 2,6 кандидата без ФСП
(было 1,4), доля кандидатов без ФСП в топ-10 относительно раздела — 0,968 (было 0,977).

Что эти числа не доказывают — перечислено в самих отчётах (разделы `threats` и `not_claimed`): релевантность
и ответы кандидатов порождены моделями команды, сложность заданий оценил автор банка, ручная разметка
не проводилась.

## Разработка

```bash
python3 -m venv .venv && .venv/bin/pip install uv   # если uv не установлен в системе
make venv        # окружение бэкенда строго по uv.lock
make dev-db      # база и почта для разработки: 127.0.0.1:5432 и 1025
make test        # pytest; каждый запуск — в своей базе test_<суффикс>
make lint        # ruff, mypy, import-linter, biome
make eval        # отчёты валидации
make openapi     # docs/api/openapi.json
make client      # клиент фронтенда из схемы
make e2e         # Playwright на поднятом стенде: вёрстка и сквозные сценарии
```

Для `make e2e` нужны зависимости фронтенда (`npm ci` в `frontend/`) и строка `ALLOWED_ORIGINS=http://web` в `.env`:
тесты ходят на стенд по внутреннему имени сервиса, и без неё вход в демо-аккаунты отклоняется проверкой `Origin`.

Если порт 5432 занят, база поднимается на другом, а тестам передаётся её адрес:

```bash
DEV_DB_PORT=55432 docker compose -f compose.yml -f compose.dev.yml up -d db mailpit
TEST_DATABASE_URL=postgresql+psycopg://app:app@127.0.0.1:55432/app make test
```

Полный список команд — `make help`.

## Известные ограничения

- Тест готов только для специализации Backend (три грейда); языковой модуль есть только для Python. В остальных
  специализациях грейд заявленный: его ничто не проверяет, кроме пометки о стаже в объяснении. Когда по такой
  специализации появится тест, перевод заявленных категорий в подтверждённые не автоматизирован.
- Вакансии с откликами и регулярные задания не реализованы.
- Разбор потребности и резюме работает по правилам и словарям, без языковой модели.
- Схема базы создаётся из метаданных моделей; миграций Alembic пока нет.
- Сервис `keycloak` в `compose.yml` (профиль `fsp`) — задел: файла realm и адаптера в сборке нет.
