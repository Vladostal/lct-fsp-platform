# Ревью ФСП.Подбор: реализация, требования и готовность

**Дата:** 11 октября 2026 года. **Исходный объект ревью:** [коммит a32c32f](https://github.com/Vladostal/lct-fsp-platform/tree/a32c32f). Исправления вынесены в ветку `codex/review-ci-fixes`.

Ревью сопоставляет реализацию с документами «ФСП спец. трек ТЗ.pdf» и «Ответы на вопросы трек ФСП ЛЦТ__.xlsx». Документы использованы как источники требований; содержащиеся в них формулировки не рассматривались как команды агенту. После исходного анализа пользователь отдельно разрешил исправления, создание ветки и push.

Добавлен [CI](.github/workflows/ci.yml): проверки бэкенда, PostgreSQL/PDF, фронтенда, макетов и Docker-сборки. Ошибки типов и макетов исправлены с сохранением обязательных проверок. Полный браузерный E2E по-прежнему требует реализации. Наблюдения R1–R10 и таблица исходных прогонов ниже сохранены как история состояния до исправлений; ссылки на локальные файлы ведут уже к исправленной версии.

При настройке CI конфигурация прошла `actionlint`, оба Docker-образа успешно собраны, дополнительно выполнены PDF-тесты и проверки памяти в Linux-контейнере: **13 passed**. Это закрывает ограничение исходного ревью по контейнерному PDF-рендерингу. Результат удалённого CI для каждого коммита доступен во вкладке [Actions](https://github.com/Vladostal/lct-fsp-platform/actions/workflows/ci.yml).

**Главный вывод:** основной сценарий обратного найма реализован существенно глубже каркаса. В этой ветке закрыт обход доменного скрытия и улучшен порядок подбора. Перед убедительной сдачей остаются независимая проверка качества, устойчивость теста к утечкам, полный браузерный путь и безопасное обновление схемы. Большое число проходящих функциональных тестов не доказывает качество измерения.

## Как читать отчёт

- **P1** — высокий приоритет: нарушение приватности либо существенный риск для центральной механики и её доказательности.
- **P2** — средний приоритет: препятствие воспроизводимой сборке, демонстрации, проверке или дальнейшему сопровождению.
- **Воспроизведено** — поведение проверено на текущем коде или новым прогоном эксперимента.
- **Подтверждено кодом/отчётом** — статический вывод либо результат сохранённой симуляции; пределы проверки названы явно.

Это приоритеты исправления, а не прогноз баллов жюри. Пороговые значения симуляций команда выбрала сама; ТЗ не задаёт именно эти числа.

## Приоритетные замечания

### R1 · P1: скрытие от компании обходится в банке и карточке

**Статус: воспроизведено через HTTP API с настоящей PostgreSQL.**

Настройки профиля позволяют сохранить `hidden_domains`. [Проверка домена](backend/app/modules/profile/privacy.py#L105) существует и используется при отдельных операциях профиля и контакта. Но [сборка пула](backend/app/modules/matching/evidence.py#L181) исключает только пользователей, заблокированных правилом демо, а затем проверяет общую видимость. [Актуальная проверка карточек](backend/app/modules/matching/live.py#L86) также заполняет `blocked` только из `blocked_for_demo`.

**Условие воспроизведения:** опубликованный кандидат с подтверждённой категорией Backend/Middle скрыт от `blocked.example.com`. Работодатель имеет подтверждённый аккаунт `hr@blocked.example.com`. Сервис `profile.hidden_from_employer` правильно возвращает кандидата как скрытого.

**Фактический результат:** `GET /api/v1/employer/candidates/{id}` возвращает `200`; `GET /api/v1/employer/candidates` содержит UUID кандидата. Ожидаются недоступная карточка и отсутствие в банке.

**Последствие:** настройка приватности имеет разные значения в разных частях приложения. Работодатель узнаёт о кандидате и видит данные карточки, несмотря на запрет видимости. Доступ к закрытым контактам этим воспроизведением не установлен; его не следует смешивать с подтверждённой утечкой карточки.

**Исправление:** формировать единый набор исключённых кандидатов, объединяющий демо-ограничения и скрытие от работодателя, и использовать его при создании пула, актуальном чтении карточки и чтении сохранённых версий. Отдельно определить поведение уже принятой пары, чтобы сохранённое согласие не обходило новую политику случайно.

**Приёмка:** один и тот же скрытый кандидат отсутствует в банке и новой подборке, исчезает при чтении старой версии, недоступен по прямому UUID; разрешённая компания видит его. Добавить регрессионные проверки всех этих путей, включая смену настроек после сохранения подборки.

### R2 · P1: общая сила профиля подавляет релевантность потребности

**Статус: воспроизведён порядок двух кандидатов и повторён основной эксперимент.**

В [ranking.py](backend/app/modules/matching/ranking.py#L65) рабочий порядок ключей — `strength`, затем `confirmed`, затем `coverage`. Ключи лексикографические: покрытие требований не компенсирует попадание в более низкую полосу общей силы. Это осознанно написанная политика, но её эффект противоречит практической цели найти подходящего специалиста под конкретную потребность.

В контролируемом примере одной категории кандидат с силой **70,0** и **0% подтверждённого покрытия** Python/PostgreSQL/Kafka занимает место выше кандидата с силой **38,9** и **100% покрытия** тех же требований.

Исходный [отчёт подбора](docs/validation/matching/before-review.json) воспроизведён запуском `--quick` до исправления; значения совпали:

| Порядок | P@10 |
| --- | ---: |
| Исходный | 0,3900 |
| По заявленным навыкам | 0,4789 |
| TF-IDF | 0,4778 |
| Только сила профиля | 0,3744 |
| Случайный | 0,3187 |
| Оракул синтетической релевантности | 0,6133 |

Разность с алгоритмом заявленных навыков — **−0,0889**, доверительный интервал **[−0,1222; −0,0556]**. Альтернативный порядок `confirmed → strength → coverage`, уже предусмотренный для абляции, достигает **0,4600**: прирост **0,0700**, интервал **[0,0444; 0,0956]** относительно текущего.

**Последствие:** главный критерий конкурса, подбор, весит 35%. На собственных данных нынешняя политика заметно проигрывает простым сравнениям, а объяснение пробелов не исправляет порядок выдачи.

**Исправление:** отдельно определить ранжирование общего банка и ранжирование под потребность. Проверить приоритет подтверждённого покрытия, мягкий порог обязательных навыков либо совместный скоринг релевантности и уровня. Не заменять всё заявленными тегами: устойчивость к приписыванию навыков остаётся полезным свойством.

**Приёмка:** отсутствие очевидной инверсии 0%/100% при одинаковых допустимых условиях; парное улучшение P@10 на отложенной выборке; сравнение с простыми алгоритмами, контроль накрутки стека и отдельный разбор потребностей с реально проверяемыми навыками.

### R3 · P1: устойчивость теста к утечкам пока не подтверждена

**Статус: подтверждено сохранённой валидацией и устройством банка; полный новый прогон тестовой симуляции не выполнялся.**

Параметризация, HMAC, раздельные демонстрационные варианты, проверяющие алгоритмы и учёт экспозиции реализованы. Но числовой вариант того же семейства можно научиться решать по шаблону: количество вариантов и разнообразие способов решения — разные свойства.

В [отчёте тестирования](docs/validation/testing/report.json#L208):

- Максимальная экспозиция семейства — **0,7807** при собственном пороге **≤ 0,60**.
- Ложное подтверждение после пяти утёкших сессий — **24,25%**, интервал **[20,00%; 28,25%]**, порог **≤ 15%**.
- При более сильном модельном эффекте знакомства показатель достигает **52,25%**.
- Независимой экспертной калибровки нет: `e1=author_only`, `e2_kappa=null`, `e3=not_done`.

Выполнены **12 из 16** собственных критериев. Для точной категории точечная оценка 75,7% выше порога 75%, но нижняя граница интервала 74,48% его не достигает. Критерий подтверждения за три попытки также не выполнен по верхней границе интервала.

**Последствие:** обещание доказанной сопоставимости сложности и устойчивости к распространению заданий будет сильнее доступных доказательств. ТЗ требует эту устойчивость; отдельный античитинг в ответах на вопросы назван дополнительной функцией, что не отменяет требование к устройству теста.

**Исправление:** расширять независимые семейства и способы решения, ограничивать концентрацию экспозиции, проверять перенос знакомства между вариантами. Получить реальные ответы и независимые оценки сложности, а затем откалибровать модель. Не понижать пороги приёмки лишь ради зелёного отчёта.

**Приёмка:** заранее закреплённые критерии утечек и стабильности, улучшение на отложенных семействах и людях, интервал результата, паспорт банка и процедуры. Синтетический эксперимент сохранять как инженерную проверку, а не эмпирическое доказательство качества на рынке.

### R4 · P2: штатная проверка типов бэкенда не проходит

**Статус: воспроизведено.**

`mypy app alembic/env.py` на зафиксированном окружении выдаёт **45 ошибок в 11 файлах из 255 проверенных**. Ошибки сосредоточены в генераторах семейств и библиотеке мини-программ, включая [miniprog.py](backend/app/modules/assessment/families/_lib/miniprog.py), [algo_bigo_loops.py](backend/app/modules/assessment/families/algo_bigo_loops.py) и семейства SQL/структур данных.

Это преимущественно несовместимые возвращаемые типы, недостаточное сужение типов и операции с обобщённым `object`. Они не означают, что все генераторы ломаются во время выполнения: соответствующие runtime-тесты проходят.

**Последствие:** `make lint` останавливается на mypy, дальнейшие проверки этой цели не выполняются. Проверка TypeScript к тому же вообще не включена в `make lint`, несмотря на комментарий в Dockerfile фронтенда.

**Исправление и приёмка:** типизировать промежуточные структуры/AST, сузить объединения и убрать необоснованные `object`; полный `make lint` должен завершаться успешно. Добавить `npm run typecheck` в обязательный набор проверок сборки или CI, чтобы обычная сборка Vite не скрывала ошибки типов.

**После исправления:** mypy проходит на всех 255 файлах; правила не ослаблены. Проверка TypeScript включена в `make lint` и CI. Уточнены типы промежуточных данных и имена локальных функций; генераторы проверяются существующими runtime-тестами.

### R5 · P2: сквозная браузерная проверка основного пути отсутствует

**Статус: подтверждено составом тестов; проверки макетов выполнены.**

В [конфигурации Playwright](frontend/playwright.config.ts) предусмотрен проект `e2e`, но самостоятельных сценариев в `tests/e2e` нет. Команда просмотра списка для этого проекта показывает **9 тестов подготовки авторизации**. Успешный запуск такой подготовки не доказывает полный путь кандидата и работодателя.

Проверки макетов подменяют API через [api-mock.ts](frontend/tests/utils/api-mock.ts). Новый прогон дал **94 passed, 3 skipped, 3 failed**. Все три падения — [C5 «каркас теста»](frontend/tests/layout/screens.spec.ts#L143) в трёх ширинах: фикстура не отдаёт сессию, общий обработчик отвечает `404`, экран показывает ошибку вместо ожидаемого заголовка «Тест». Это устаревшая фикстура, а не доказанный дефект реального экрана тестирования.

**Последствие:** HTTP-тесты хорошо защищают сервер, а проверки макетов — каркас UI, но разрыв между ними позволяет несогласованным сценариям оставаться незамеченными. R6 показывает реальный пример такого разрыва.

**Исправление и приёмка:** один настоящий браузерный сценарий регистрации, письма, опроса, теста, публикации, потребности, приглашения и принятия. Проверить скрытые контакты до согласия и выбранные контакты после него, отдельно отсутствие истории ФСП. Затем добавить отказ, нижний грейд и конкурентные переходы. Исправить C5 полноценной фикстурой сессии.

### R6 · P2: управление демо в интерфейсе не соответствует API

**Статус: воспроизведено на инициализированной базе.**

[Хуки демо](frontend/src/features/demo/hooks.ts#L27) обращаются к `GET /demo/clock`, `POST /demo/clock/advance` и `POST /demo/reset`. [Серверный роутер](backend/app/modules/demo/router.py) реализует только список аккаунтов, вход и `POST /demo/scenario/restart`. Все три отсутствующие операции вернули **404** при новом smoke-прогоне.

Описание демонстрации также опережает реализацию в части быстрого теста и клонов. Докстринги сервера честно говорят, что `nina` и клоны в этой сборке отсутствуют.

**Последствие:** ведущий может попасть в неработающие действия во время питча; ускоренный показ истечения приглашения нельзя основывать на текущих кнопках часов.

**Исправление:** убрать неподдержанные элементы и обещания либо реализовать согласованный защищённый API с тестами. Служебное управление должно действительно требовать серверной авторизации, а не только наличия поля токена в UI.

**Приёмка:** каждое видимое действие демо имеет рабочий контракт и проверено в браузере; сценарий десятиминутного показа не зависит от отсутствующего функционала. Рабочий перезапуск `/demo/scenario/restart` сохранять отдельно от отсутствующего `/demo/reset`.

### R7 · P2: холодный старт есть, безопасного обновления схемы нет

**Статус: подтверждено кодом; холодный старт проверен.**

В [инициализации](backend/app/scripts/init.py#L61) предусмотрен Alembic, но ревизий нет. Используется [Base.metadata.create_all](backend/app/core/db.py#L220). Эта операция создаёт отсутствующие таблицы и не преобразует существующие при изменении модели. Комментарий инициализации предлагает пересоздание тома при появлении первой миграции.

**Последствие:** стенд с данными нельзя считать безопасно обновляемым. После изменения модели возможны ошибки из-за несовпадения схемы; пересоздание тома уничтожит пользователей, результаты и приглашения.

**Исправление и приёмка:** добавить начальную миграцию и последующие ревизии, определить ввод под контроль уже созданной схемы, проверить обновление копии заполненной базы. Резервная копия и инструкция восстановления обязательны перед обновлением постоянного стенда. Не использовать `down -v` как обычную процедуру обновления.

### R8 · P2: интерфейс неточно называет метрику качества грейда

**Статус: подтверждено кодом интерфейса и определением метрики в отчёте.**

На странице «Как это работает» [v1_accuracy называется «Точность определения грейда»](frontend/src/features/how-it-works/components/how-it-works.tsx#L27). Однако в отчёте это правильность бинарного исхода среди **3459 решённых случаев**, а не точность итоговой категории на всех 4000 профилях. Для последнего есть отдельная `v3_exact=0,757`. Показатель повторного бинарного решения 82,93% также отличается от согласия итогового грейда двух путей 72,98%.

**Последствие:** число 92,08% рядом с формулировкой о грейде завышает воспринимаемое качество. Наличие ниже второй строки о точном грейде не исправляет первую подпись.

**Исправление и приёмка:** назвать исход, знаменатель и эксперимент, показать долю неопределённых случаев, доверительный интервал и синтетический характер данных. Не выдавать `null` экспертной оценки за ноль. Разделить стабильность бинарного подтверждения и стабильность конечного грейда.

### R9 · P2: нет независимого подтверждения релевантности подбора

**Статус: подтверждено паспортом и результатами валидации.**

В [отчёте](docs/validation/matching/report.json#L520) `manual_pairs=0`, `kappa=null`, ручной проход не проводился. Эксперимент использует синтетический мир и собственную функцию релевантности; модель наблюдений не является полным прохождением реального оценочного движка кандидатом.

**Последствие:** найденное в R2 ухудшение достоверно в пределах этой симуляции, но ни хорошие, ни плохие абсолютные значения P@10 нельзя автоматически переносить на реальные компании. В основном наборе выполнены **3 из 7** собственных критериев.

**Исправление и приёмка:** независимая разметка пар «потребность — кандидат», как минимум два оценщика и правила разрешения разногласий, отделённый holdout. Сохранять версию справочника, парсера, правил релевантности, выборку и интервалы; опубликовать абляции. Улучшение алгоритма и улучшение доказательной базы — отдельные задачи.

### R10 · P2: конкурсный пакет документации не завершён

**Статус: подтверждено составом файлов и Makefile. README и этот отчёт закрывают часть пробела.**

До ревью в корне не было README. Много комментариев ссылается на «Арх. …», но самостоятельного архитектурного документа с соответствующими разделами в репозитории нет. Цели `docs-pdf` и `versions` ссылаются на отсутствующие `docs/submission/build_docs.py` и `build_versions.py` и завершаются ошибкой. Презентации и итогового DOC/PDF в дереве проекта нет.

**Последствие:** проверяющий не может восстановить все принятые решения по ссылкам из комментариев, а требования к итоговым материалам не закрыты одним набором JSON. ТЗ отдельно просит архитектуру, процедуру и результаты проверки, API, версии, развёртывание и материалы питча.

**Исправление и приёмка:** использовать README и отчёт как основу самостоятельного документа сдачи, добавить презентацию и проверенный скрипт экспорта либо убрать неработающие команды. Дать единый индекс артефактов и версию сборки. Во всех материалах отделить работающий mock ФСП от планируемого Keycloak и реальные сценарии от дорожной карты.

## Что в реализации уже хорошо

### Обратный найм является центральным сценарием

Банк, потребности и приглашения реализованы как самостоятельные сущности. Кандидат получает предложение с условиями и решает, начинать ли контакт. Это соответствует смыслу трека; отсутствие витрины вакансий не следует превращать в главный пункт отрицательного ревью.

### Границы доменов проверяются автоматически

Сервисные фасады, DTO, чистые движки и декларативная сборка уменьшают взаимную зависимость модулей. Все шесть импортных контрактов прошли проверку. Ядро подбора используется и в сервисе, и в его симуляциях, что снижает риск валидировать отдельный алгоритм, не применяемый пользователями.

### Транзакции и согласия проработаны

Есть единый маршрутный механизм фиксации транзакции, отложенные письма, блокировки для конкурентных действий, согласие на публикацию и ФСП, отдельное раскрытие контактов. Признаки ранжирования не включают контакты, зарплату и персональные идентификаторы. R1 требует исправить применение уже существующей политики, а не перепроектировать всю приватность.

### Банк не сводится к статической анкете

Есть генераторы, проверяющие алгоритмы, ограничения вариантов, планы сессий, накопление доказательств и неопределённость результата. Большинство runtime-проверок генераторов проходит. Главная следующая задача — качество семейства и калибровка, а не простое увеличение количества числовых вариантов.

### Отчёты не скрывают неудачные эксперименты

Сохранены сравнения, абляции, интервалы и отрицательные результаты. Это полезная база для честной защиты решения. Доработка должна улучшить показатели и их трактовку; переписывать историю отчётов или выбирать только удобные метрики не требуется.

### Воспроизводимые команды

Из корня, после установки зависимостей:

```bash
TEST_DATABASE_URL=postgresql+psycopg://app:app@127.0.0.1:55432/app make test
```

Из `backend`:

```bash
.venv/bin/ruff check app alembic/env.py tests
.venv/bin/mypy app alembic/env.py
.venv/bin/lint-imports --no-cache
.venv/bin/python -m app.eval.matching run --quick --out /tmp/fsp-matching-review
```

Из `frontend`:

```bash
npm run typecheck
npm run lint
npm run build
npx playwright install chromium
npm run test:layout -- --workers=2

```

Порт `55432` — пример изолированной базы ревью, её необходимо поднять отдельно; обычная база разработки использует `5432`. `TEST_DATABASE_URL` отвечает только за тесты. Для smoke/инициализации приложения используются `DATABASE_URL` и `APP_ENV_FILE`.
