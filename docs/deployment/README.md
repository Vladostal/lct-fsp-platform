# Публичный стенд и доставка релизов

Адрес: **https://fsp.185.125.203.132.sslip.io**. DNS имени содержит IP сервера; Caddy получает и обновляет публичный сертификат автоматически. Домен временный: при переезде нужно заменить `FSP_DOMAIN` и `PUBLIC_BASE_URL` в серверном окружении.

## Изоляция на общем сервере

Стенд расположен в `/home/fedya/fsp-platform`, Compose-проект — `fsp-platform`. Он использует самостоятельный `compose.production.yml`, сеть `172.28.8.0/24`, собственные тома `fsp-platform_db-data`, `fsp-platform_tls-data`, `fsp-platform_tls-config`. Единственные внешние порты — **80 и 443**. PostgreSQL, API и Mailpit наружу не публикуются. Caddy имеет адрес `172.28.8.2`; только этот адрес доверен nginx, а API доверяет внутренней сети стенда.

Существующий проект `vehicle-reid` на порту **8080** не входит в команды развёртывания. Деплой не останавливает чужие контейнеры, не изменяет Docker daemon и не выполняет глобальную очистку образов или томов. Перед первым запуском нужно проверить свободные порты и отсутствие пересечения подсетей.

Ограничения памяти: PostgreSQL 384 МБ, API 768 МБ, инициализация 1024 МБ, nginx 64 МБ, Mailpit 64 МБ, Caddy 128 МБ. Инициализация завершается до запуска новой версии API. Ограничения CPU позволяют соседнему проекту продолжать работать, но не заменяют измерение общей нагрузки сервера.

## Структура сервера

```text
/home/fedya/fsp-platform/
├── bin/receive_release.py    # установленный администратором приёмник SSH
├── bin/deploy.sh            # установленный администратором сценарий
├── shared/.env             # постоянные секреты, права 600
├── releases/<commit-sha>/   # конфигурация и данные конкретного релиза
├── current -> releases/... # последний успешно проверенный релиз
├── backups/*.dump          # резервные копии перед обновлениями
├── incoming/               # временные файлы приёмника
└── state/                  # блокировка и SHA текущего релиза
```

Скрипты из `bin` автоматически не заменяются содержимым релиза. Их обновляет оператор, проверив изменения в `infra/deploy`. Секреты не входят ни в Git, ни в архив релиза. База и TLS-сертификаты хранятся в постоянных томах. При повторном запуске ключ генерации тестов сохраняется.

## GitHub Actions

1. CI на каждом push проверяет Python, типы, импорты, PostgreSQL-тесты, PDF, интерфейс, макеты, образы и приёмник архивов.
2. Для push в `main` CI сохраняет два образа с тегом полного SHA в **закрытые артефакты репозитория** на 7 дней. Образы не публикуются в открытый реестр.
3. CD получает событие завершения CI. Он проверяет успешный результат, имя workflow, ветку, репозиторий и соответствие SHA текущему `main`.
4. Он забирает именно проверенные образы, добавляет runtime-файлы и SHA-256 каждого файла, повторно проверяет `main` и доставляет архив по SSH.
5. Приёмник отвергает абсолютные пути, `..`, ссылки, повторяющиеся имена, лишние файлы, неверные контрольные суммы и архивы больше 2,5 ГБ.
6. На сервере блокировка допускает только один деплой. Образы загружаются, база резервируется, выполняется инициализация; затем проверяются контейнеры и **HTTPS** `/healthz`, `/api/v1/health`. Только после успеха обновляется `current`.

CD использует environment `production`. В **Settings → Secrets and variables → Actions** нужны:

| Тип | Имя | Содержимое |
| --- | --- | --- |
| Secret | `FSP_DEPLOY_KEY` | Приватная часть отдельного ключа доставки |
| Secret | `FSP_KNOWN_HOSTS` | Проверенный ED25519 host key сервера; проверка хоста обязательна |
| Variable | `FSP_SSH_HOST` | `185.125.203.132` |
| Variable | `FSP_SSH_USER` | `fedya` |

Для SSH-ключа на сервере применяется `restrict`, срок действия и принудительная команда `/home/fedya/fsp-platform/bin/receive_release.py`. Интерактивная оболочка, проброс портов, агент и PTY запрещены. Ключ позволяет доставлять исполняемый релиз приложения, поэтому его следует считать чувствительным доступом к развёртыванию. Не используйте личный SSH-ключ разработчика. По истечении срока ключ нужно заменить, обновив GitHub secret и строку `authorized_keys`; удаление строки немедленно отзывает доступ.

Повторить доставку можно через **Actions → CD → Run workflow**, указав ID успешного push-CI для **текущего** `main`. Просроченные артефакты требуют нового успешного push-CI; релиз другой ветки или устаревшего `main` отвергается.

## Первый запуск

Оператор устанавливает два скрипта из `infra/deploy` в `bin` и делает приёмник исполняемым. Из `.env.example` создаётся `shared/.env` с `APP_ENV=production`, случайными `ASSESSMENT_SECRET`, `ADMIN_TOKEN`, `DB_PASSWORD`, паролем Mailpit; `DATABASE_URL` использует `DB_PASSWORD`. Обязательны:

```dotenv
APP_ENV=production
PUBLIC_BASE_URL=https://fsp.185.125.203.132.sslip.io
FSP_DOMAIN=fsp.185.125.203.132.sslip.io
COOKIE_SECURE=true
STAND_SUBNET=172.28.8.0/24
TRUSTED_PROXY_CIDRS=172.28.8.0/24
CADDY_IP=172.28.8.2
NGINX_REAL_IP_FROM=172.28.8.2
DEMO_PUBLIC_RESTART=false
```

Настройки почты и остальные обязательные переменные сохраняются из шаблона. Не заменяйте окружение при каждом релизе: смена `ASSESSMENT_SECRET` меняет варианты банка. Права на `shared` — 700, на `.env` — 600.

Для первого релиза без автоматического ключа оператор может передать архив обычным разрешённым SSH-сеансом и запустить установленный приёмник, подав архив на stdin. Упаковка:

```bash
python3 infra/deploy/package_release.py \
  --sha "$COMMIT_SHA" --images /path/to/images --output /path/to/release.tar
```

В каталоге images должны находиться `backend.tar.gz` и `frontend.tar.gz`, созданные из образов `fsp-podbor-backend:$COMMIT_SHA`, `fsp-podbor-frontend:$COMMIT_SHA`. На x86-сервере образы должны иметь архитектуру `linux/amd64`.

## Резервные копии и восстановление

Перед обновлением работающей базы сохраняется `pg_dump -Fc` только базы ФСП. Копии остаются в `backups` с правами владельца; перенос на отдельный носитель и срок хранения настраиваются оператором. Автоматическая очистка Docker отсутствует: периодически проверяйте свободное место, удаляйте только ненужные релизы и образы ФСП.

При ошибке запуска автоматически возвращаются образы и конфигурация предыдущего релиза. **База автоматически не откатывается**: инициализация и сид могут менять данные. Восстановление dump выполняется оператором после остановки только API ФСП и проверки необходимости потери записей, созданных после backup. Не применяйте `docker compose down -v` к публичному стенду.

В репозитории пока нет версионированных миграций схемы. Поэтому CD сравнивает fingerprint `models.py`, перечислений, настройки базы и файлов Alembic: если он изменился, обновление **останавливается до изменения базы**. Это консервативная защита, иногда она блокирует даже комментарий в модели. Для изменения схемы сначала нужна проверенная миграция, резервная копия и отдельная процедура перехода; принудительное пересоздание тома не является миграцией.

Для ручного возврата выберите сохранённый совместимый релиз, затем запустите его Compose с обоими файлами окружения:

```bash
ROOT=/home/fedya/fsp-platform
RELEASE="$ROOT/releases/<previous-commit-sha>"
docker compose -p fsp-platform \
  --env-file "$ROOT/shared/.env" --env-file "$RELEASE/.images.env" \
  -f "$RELEASE/compose.production.yml" \
  up -d --wait db mailpit api web caddy
```

После проверки HTTPS обновите `current` и `state/deployed-sha`. Никогда не выбирайте релиз с несовместимой схемой. Дополнительно проверьте старый сайт `http://127.0.0.1:8080/` и состояние его контейнеров.
