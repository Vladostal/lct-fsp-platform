# CLAUDE.md — платформа подбора ИТ-специалистов (хакатон, трек ФСП)

Этот файл — контекст проекта для Claude Code. Здесь собраны требования ТЗ, принятые архитектурные решения, распределение ролей и план. Оригинал ТЗ стоит положить в репозиторий как `docs/tz.pdf` и сверяться с ним при спорных вопросах.

---

## 1. Суть задачи

Веб-сервис для подбора ИТ-специалистов с **обратной механикой**: соискатели автоматически распределяются по категориям на основе объективно подтверждённого профиля, а **инициативу проявляет работодатель** — он находит нужную категорию и сам направляет приглашение конкретному кандидату с описанием предложения и зарплатой (ориентир — модель LHH). Это смысловой центр конкурса и главный критерий оценки.

Это **не** парсер сторонних сайтов и не витрина чужих вакансий: платформа напрямую связывает только работодателя и соискателя.

### Ключевые правила из ТЗ (обязательные)

- **Категория = специализация + грейд** (например, «Backend · Middle»). Определяется **только** обязательным путём при регистрации: опрос по отрасли и специализации → самостоятельный выбор грейда → тест на заявленный грейд. Самоописанное резюме на категорию не влияет.
- **Внутри категории ранжирование** по силе подтверждённого профиля: результаты тестов и достижения ФСП. Выдача поиска ранжируется по соответствию потребности работодателя **с краткой объяснимостью**.
- **Тестирование:** единый набор заданий для всех не подходит (утечки), генерация нейросетью под каждого не гарантирует сопоставимую сложность. Нужен подход, устойчивый к обеим проблемам. Нужно показать, как по нескольким описаниям вакансий система формирует задания.
- **Грейд по итогам теста не понижается принудительно:** не прошёл — можно пройти тест на уровень ниже; уверенно прошёл — можно повысить. Смена грейда не чаще раза в N времени (у нас **90 дней**).
- **Зарплата обязательна** в вакансии и в приглашении: диапазон «от–до» в рублях. Кандидат видит условия до начала общения.
- **Приглашение** содержит описание предложения, зарплату, название компании и способ связи.
- **Контакты кандидата раскрываются работодателю только** после того, как кандидат принял приглашение или откликнулся сам.
- **Статусы** приглашений и откликов (отправлено, просмотрено, принято, отклонено); обе стороны видят актуальный статус.
- **Регистрация по email с подтверждением адреса.** Верификация компаний и модерация вакансий в MVP не нужны.
- **Связь профиля с ID участника ФСП.** ФСП ID в будущем будет на Keycloak (совместимость приветствуется). API и структура данных ФСП **не предоставляются** — придумываем сами. **Обязательно** корректно обрабатывать кандидата без истории ФСП.
- **Фильтрация и уточнение запроса без потери ранее полученной подборки.**
- Датасетов нет — работаем на синтетических данных и **предлагаем собственную процедуру валидации** с результатами.

### Функциональность MVP по ролям

**Кандидат:**
- профиль и резюме: вручную или загрузка PDF с автораспознаванием (ФИО, контакты, стек, грейд, роли, стаж, софт-скиллы); автогенерация стандартизированного PDF-профиля;
- опрос → выбор грейда → тест → категория;
- категория и грейд: текущий статус, история опросов и тестов, пересдача на грейд выше/ниже с ограничением частоты;
- входящие приглашения: принять / отклонить;
- настройки: приватность, согласие на обработку данных (152-ФЗ), связь с ФСП ID;
- видит только свои приглашения и отклики.
- *Желательно:* регулярные короткие задания от работодателей; список вакансий и самостоятельный отклик.

**Работодатель:**
- профиль компании;
- описание потребности (специалисты, чем занимается команда, стек, специализация, грейд) → подборка;
- подборка: рекомендованные категории и кандидаты с обоснованием;
- поиск по всей базе: фильтры по специализации, грейду, категории, стеку, наличию достижений ФСП;
- приглашение конкретному кандидату (без обязательной привязки к вакансии), отслеживание статусов;
- не видит контакты кандидата до принятия приглашения или отклика.
- *Желательно:* публикация вакансий и работа с откликами.

**Вне MVP, только концепция:** защита от фиктивных вакансий и недобросовестных работодателей, интеграция с ATS.

### Нефункциональные требования

- Разделение Frontend / Backend / слой хранения; допустим монолит с явными слоями и слабо связанными модулями.
- Docker + docker-compose (плюс к оценке); воспроизводимый запуск по инструкции.
- **OpenAPI (Swagger)** для всех методов: запросы, ответы, коды ошибок.
- Безопасность: 152-ФЗ, согласия, роли, безопасное хранение паролей и токенов.
- Открытый код без обфускации, лицензии MIT/Apache/BSD.
- Работа на недорогом VPS: память держать в разумных пределах.
- Десятки одновременных пользователей; подборка, профиль и поиск за приемлемое время.
- Сложные места кода комментируются.

### Критерии оценки (веса задают приоритеты)

| Критерий | Вес |
|---|---|
| Новая механика подбора (сценарий контакта, ранжирование, объяснимость; проверка долей релевантных в топе) | **35%** |
| Механика тестирования, валидация, категоризация (устойчивость к утечкам, стабильность грейда, дискриминативность, процедура валидации) | **25%** |
| Удобство интерфейса | 10% |
| Презентация и питч | 10% |
| Техническая проработка | 7% |
| Дополнительный функционал (отклики/вакансии, регулярные задания, концепция антифрода и ATS, мобильная вёрстка) | 7% |
| Полнота реализации и документация (в т.ч. кандидат без истории ФСП) | 6% |

### Что сдаём

- **Промежуточно:** репозиторий, краткое описание механик подбора и тестирования с обоснованием, демо базового сценария.
- **Финально:** репозиторий, презентация (pptx/pdf), развёрнутый прототип (или видео + инструкция), сопроводительная документация (doc/pdf).
- **Документация обязана содержать:** функциональную и компонентную архитектуру; механику тестирования с обоснованием устойчивости к утечкам; механику подбора и категоризации; процедуру валидации и результаты; схему интеграции с реестром ФСП; описание API; библиотеки **с версиями**; пошаговую инструкцию сборки, развёртывания и запуска.
- **Демо обязано показать сквозной сценарий:** регистрация соискателя → опрос и тест → категория → работодатель ищет категорию → приглашение конкретному человеку (→ отклик на вакансию, если реализован). Отдельно объяснить механики тестирования и подбора.

## 3. Архитектура (фактическая)

Разделы 3 и 4 описывают то, что реально лежит в репозитории, а не первоначальный план. Отличия от плана собраны
в конце раздела 3. Запуск, команды и версии библиотек — в `README.md`.

**Модульный монолит на FastAPI** + PostgreSQL + SPA на React. Один процесс `api`, фоновые задачи — цикл внутри
него (`core/background.py`). Наружу опубликован только nginx сервиса `web`.

```
web (nginx + SPA) ──/api──▶ api (FastAPI) ──▶ db (PostgreSQL 18)
        │                       │
        └──/mail/──▶ mailpit    └── демо-ФСП (OIDC + реестр) смонтирован в /api/fsp-mock
```

### Стек

| Слой | Что используется |
|---|---|
| API | FastAPI, Pydantic v2, SQLAlchemy 2 (синхронный, psycopg 3), Python 3.13, uv |
| БД | PostgreSQL 18; схема создаётся из метаданных (`core.db.create_schema`), миграций Alembic пока нет |
| Аутентификация | своя: cookie-сессия `sid`, argon2, письма подтверждения через Mailpit |
| Разбор текста | правила и словари (`textparse`), pymorphy3, rapidfuzz; языковая модель не используется |
| PDF | pypdf и pdfplumber (чтение резюме), WeasyPrint (PDF-профиль) |
| Фронт | React 19, TypeScript, Vite, TanStack Router и Query, Tailwind 4, клиент из OpenAPI (`@hey-api/openapi-ts`) |
| Качество | ruff, mypy, import-linter, pytest, biome, Playwright (вёрстка на перехвате запросов и сквозные на стенде) |

### Структура репозитория

```
backend/app/
  core/        # конфиг, БД и транзакции, сессии, ошибки, почта, часы сервиса, фоновый цикл
  shared/      # перечисления, вилка, общие схемы
  modules/     # identity, catalog, reports, company, textparse, assessment, profile, fsp, matching, contact, demo
  fsp_mock/    # демо-провайдер ФСП ID и демо-реестр (отдельное ASGI-приложение)
  eval/        # симуляции валидации: testing, matching, contact
  seed/        # демо-данные и сценарий
  scripts/     # init (схема, банк, сид), export_openapi
  wiring.py    # единственное место подключения модулей (строки «модуль:атрибут», ленивая загрузка)
backend/tests/ # зеркалит модули; своя база на каждый запуск pytest
frontend/      # src/features/<домен>, src/routes, src/client (генерируется), tests/layout, tests/e2e
docs/          # api/openapi.json, fsp-registry-openapi.json, validation/*/report.json
infra/nginx/   # шаблон конфигурации nginx
compose.yml, compose.dev.yml, Makefile, README.md
```

### Соглашения по модулям

- Слои (снизу вверх): `identity | catalog | reports` → `company | textparse` → `assessment` → `profile | fsp` →
  `matching` → `contact` → `demo`. Импорт только вниз; модули одного слоя независимы.
- Чужой модуль виден только через его `service.py` и `dto.py`. Обе проверки делает `import-linter` (`make lint`).
- Чистые ядра (`assessment/engine`, `matching/scoring.py`, `matching/ranking.py`, `fsp/signal.py`,
  `contact/rules.py`) не импортируют SQLAlchemy: их же вызывают симуляции в `app/eval`.
- Роутеры создаются как `APIRouter(route_class=TxRoute)`; у обработчика есть явный `summary` либо docstring — из его первого
  предложения берётся название метода в Swagger.
- Тексты ошибок: клиент берёт свой по `code` (`frontend/src/content/errors.ts`), `message` сервера — запасной,
  но он обязан быть человеческим текстом, а не кодом.
- Время берётся из `core.clock` (`now(db)` — время сервиса), SQL-функции времени в доменном коде запрещены.
- Кого работодатель не видит вовсе, решает одна функция — `matching.evidence.blocked_for`: демо-работодатель видит
  только демо-кандидатов, а кандидат из списка «не показывать компаниям» скрыт от домена почты работодателя.
- Демо-сценарий привязан ко времени: приглашения `anna` и `ivan` живут 5–6 дней. Устаревший и никем не занятый
  сценарий пересоздаёт фоновая задача `demo.service.refresh_scenario` (`DEMO_AUTO_RESTART`, по умолчанию включена).

### Отличия от первоначального плана

Сделано проще, чем планировалось: нет Keycloak для своих пользователей, Redis и arq, pgvector и эмбеддингов,
GigaChat и YandexGPT, Caddy. Модули называются иначе (`identity`, `profile`, `company`, `contact`, `assessment`,
`textparse`). Вакансии с откликами и регулярные задания из сборки убраны. Адаптер `FSP_MODE=keycloak`
не реализован.

## 4. Ключевые механики (фактические)

### 4.1 Тестирование (25% оценки)

- **Задание — генератор** (`assessment/families/*.py`): по сиду строит условие, ключ считается кодом и сверяется
  независимым оракулом. 31 семейство, 2–3 уровня, по 60 вариантов на уровень; банк собирается при инициализации.
- Сид варианта — HMAC от `ASSESSMENT_SECRET`, идентификатора семейства, **версии семейства**, уровня и номера.
  При любом изменении `generate` версия семейства увеличивается на 1: это меняет все его варианты.
- Генерация обязана быть детерминированной и не зависеть от `PYTHONHASHSEED` (нельзя обходить множества строк);
  приёмка семейства не должна зависеть от значения секрета — оба свойства закреплены в
  `tests/assessment/test_determinism.py`.
- **Форма теста** не адаптивная: 14 заданий по плану тем грейда, при исходе «на границе» — до двух блоков по 6.
  Оценка уровня — апостериорное распределение на сетке, наклон заданий один; сложность `b` — оценка автора.
- **Правила грейда** (`engine/rules.py`): не подтвердил — тест на грейд ниже; подтвердил с запасом — на грейд выше;
  смена грейда раз в 90 дней; повтор того же грейда через 14 дней; не больше трёх сессий за 30 дней.
- **Быстрый демо-тест** (только при `DEMO_MODE`, `POST /demo/assessment/quick-session`): 12 ответов из 14 подставлены.
  Сессия помечена `demo_prefilled`, категория — `is_demo_result`. Подставленные ответы идут в зачёт только этой
  сессии (`repo.window_items(include_prefilled=...)`): в результат обычного теста они не попадают никогда, паузу
  «тот же грейд» такая сессия не даёт.
- Доступен только Backend (junior, middle, senior); языковой модуль — только Python.
- Валидация: `python -m app.eval.testing` → `docs/validation/testing/report.json`.

### 4.2 Подбор (35% оценки)

1. Текст потребности разбирает `textparse` по правилам; работодатель правит поля.
2. Фильтр-условие — общий формат работы. Разделы категорий: основная, грейд ниже с запасом, грейд выше.
3. **Порядок внутри раздела** (`ranking.DEFAULT_KEY_ORDER`, версия оценщика `match-2`): закрытые обязательные
   навыки → подтверждённое покрытие → сила профиля → покрытие заявленным. Порядок лексикографический, баллы
   не складываются. Прежний порядок «сила первой» проигрывал бейзлайну и оставлен только абляцией отчёта.
4. Объяснение строки строится из тех же величин: доводы, риск, источник каждого навыка.
5. Версии подборки: уточнение создаёт новую версию с `parent_id`, прежние остаются, есть сравнение версий.
6. Приглашение: `sent → viewed → accepted / declined / expired`, плюс `bounced` (вилка ниже скрытого минимума).
- Валидация: `python -m app.eval.matching run` → `docs/validation/matching/report.json`. После изменения порядка
  или констант отчёт пересобирается, `SCORER_VERSION` увеличивается.

### 4.3 Интеграция с ФСП

- Привязка — OIDC Authorization Code с PKCE к демо-провайдеру `fsp_mock`; реестр — его же REST
  (`docs/fsp-registry-openapi.json`). Шлюз — `fsp/gateway` (`MockFspGateway`).
- Кандидат без истории ФСП: вклад в силу профиля равен нулю, штрафа нет, в карточке нейтральный текст.

### 4.4 Резюме

- PDF читается в отдельном процессе с пределом времени и памяти; поля извлекаются правилами
  (`profile/resume`). Файл и текст не сохраняются. Резюме на категорию не влияет.

| 4 | **Frontend + подача** | оба кабинета, брендбук ФСП, адаптивная вёрстка; до готовности бэкенда работает на моках из OpenAPI (MSW или Prism); презентация, демо-видео, сценарий питча |

**Документация** — каждый пишет свой раздел, тимлид сводит:
- архитектура, API, версии, инструкция запуска — роль 1;
- тестирование и его валидация — роль 2;
- подбор, категоризация, интеграция ФСП, валидация подбора — роль 3.

## 6. План и точки синхронизации

**Старт (до кода):**
- схема БД;
- OpenAPI основных эндпоинтов;
- внутренние интерфейсы:
  - `TestEngine`: `start(candidate, specialization, grade)`, `next_item(session)`, `submit(session, answer)`, `result(session) -> (grade, theta)`;
  - `Matcher`: `rank(need) -> list[RankedCandidate]` (с компонентами score и текстом объяснения).

**К промежуточной сдаче** — работает сквозная цепочка, пусть упрощённо: регистрация → опрос → короткий тест (можно без CAT) → категория → работодатель находит кандидата → приглашение → принятие с раскрытием контактов. Упрощённые реализации `TestEngine` и `Matcher` затем подменяются полноценными без поломки цепочки.

**Деплой** поднять рано (к концу 2-го дня), хотя бы с заглушками.

**За день до финала** — заморозка фич: баги, сиды, демо-прогон, документация, презентация.

## 7. Как работать с Claude Code в этом репозитории

- Перед реализацией фичи сверяться с разделом 1 (обязательные правила) — особенно раскрытие контактов, обязательная зарплата, категория только из тестов, кандидат без ФСП.
- Не добавлять зарубежные LLM API и не отправлять необезличенные персональные данные во внешние сервисы.
- Не менять границы модулей и контракты `TestEngine` / `Matcher` без явного решения команды.
- Для каждого нового эндпоинта: схемы Pydantic, `response_model`, коды ошибок, проверка роли, тест.
- Новые зависимости — с фиксированной версией в lock-файле.

5. Миграции Alembic, адаптер настоящего Keycloak для ФСП ID.
6. Демо-приглашение живому кандидату от демо-компании и экран списка «не показывать компаниям» (есть только API).
